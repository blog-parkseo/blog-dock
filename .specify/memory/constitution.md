# blog-dock Constitution

티스토리형 블로그 서비스 blog-dock을 Spec Kit 방식(명세 → 계획 → 작업 → 구현)으로 만들 때 지키는 원칙이다.
기준 문서는 「티스토리형 블로그 요구사항 명세서」(2026-10-05)와 그 원본인 「티스토리형 블로그 통합 기능명세서 v0.2」다.

## Core Principles

### I. 사용자가 확인할 수 있는 규칙 (What before How)

- 명세(`spec.md`)에는 "서비스 밖에서 사용자로서 확인할 수 있는 규칙"만 적는다.
- 언어, 프레임워크, DB, 화면 구성, 문구 같은 구현 방법은 계획(`plan.md`) 이후 단계에서 정한다.
- 모든 요구사항은 테스트할 수 있어야 한다. "적절히", "빠르게"처럼 확인할 수 없는 표현은 쓰지 않는다.

### II. 기능 ID 추적성

- 모든 기능은 통합 기능 ID(`영역코드-번호`, 예: `POST-03`)로 부른다. 영역코드는 AUTH, BLOG, POST, CAT, TAG, CMT, SOC, SUB, SRCH, HOME, MNG, ADMIN, COM이다.
- 명세, 계획, 작업(`tasks.md`), 이슈, 커밋, PR에서 같은 ID를 쓴다. 비기능 요구사항은 `NFR-01`~`NFR-15`를 쓴다.
- 삭제된 번호는 다시 쓰지 않고, 새 기능은 영역의 끝 번호에 붙인다.

### III. P0 우선 (NON-NEGOTIABLE)

- P0 24개 기능을 먼저 끝까지 완성한다. P0만으로 "가입 → 블로그 개설 → 글 발행 → 홈에서 발견 → 읽기·댓글·공감" 흐름이 동작해야 한다.
- P1은 P0가 모두 동작한 뒤, P2는 여유가 있을 때 구현한다.
- 각 사용자 스토리는 따로 구현하고 따로 시연할 수 있어야 한다.

### IV. 서버에서 지키는 권한과 보안

- 권한은 화면에서 버튼을 숨기는 것으로 끝나지 않는다. 주소를 직접 입력하거나 요청을 직접 보내도 같은 결과가 나와야 한다.
- 남의 비공개 글은 403이 아니라 404로 처리해 존재 자체를 숨긴다.
- 사용자가 입력한 내용의 스크립트는 어디에 보여도 실행되지 않는다. 내부 오류 정보는 사용자에게 보이지 않는다.

### V. 신뢰할 수 있는 데이터

- 같은 요청을 연달아 보내도 한 번만 처리한다(글 발행, 댓글, 공감, 구독).
- 공감·댓글·구독자·글 수는 새로고침하면 언제나 실제 값과 같다.
- 여러 단계가 함께 처리되는 작업(글 삭제, 카테고리 삭제, 블로그 이사)은 일부만 처리된 상태로 남지 않는다.
- 저장에 실패하거나 로그인이 만료돼도 사용자가 쓰던 내용을 잃지 않는다.

### VI. 단순함

- 명세에 없는 기능은 만들지 않는다. 필요하면 먼저 명세를 고친다.
- 처음에는 가장 단순한 구조로 만들고, 복잡함이 필요하면 `plan.md`의 Complexity Tracking에 이유를 적는다.

## 범위와 제약

- 포함: 회원·인증, 블로그, 글, 카테고리, 태그, 댓글·방명록, 반응, 구독·피드·알림, 검색, 홈·탐색, 블로그 관리, 서비스 관리, 공통의 13개 영역.
- 제외: 광고·결제, 모바일 앱, 이메일·푸시 알림, 개인 도메인 연결, 스킨 HTML·CSS 직접 편집.
- 날짜와 시각은 한국 시간 기준으로 보여 준다. 최신 크롬·사파리·엣지와 휴대폰 화면 폭에서 P0 기능이 동작해야 한다.

## 개발 흐름

1. `/speckit-specify` 또는 `specs/NNN-*/spec.md` 수정으로 명세를 정한다.
2. `/speckit-clarify`로 애매한 부분을 묻고 답을 명세에 반영한다.
3. `/speckit-plan`으로 기술 스택과 설계(data-model, contracts)를 정한다.
4. `/speckit-tasks`로 기능 ID별 작업 목록을 만든다.
5. `/speckit-implement`로 작업 순서대로 구현한다.
6. 변경은 브랜치와 PR로 올리고, PR 설명에 관련 기능 ID를 적는다.

## Governance

- 이 원칙은 다른 개발 관행보다 우선한다. 계획과 PR 리뷰에서 원칙을 지켰는지 확인한다.
- 원칙을 바꾸려면 이 문서를 고치고, 버전을 올리고, 위 Sync Impact Report에 이유를 남긴다.
  - MAJOR: 원칙을 빼거나 뜻을 바꿈 / MINOR: 원칙·섹션 추가 / PATCH: 표현 다듬기
- 팀 공통 명세(통합 기능명세서)가 바뀌면 `spec.md`를 함께 고친다.
